# The Quickieweb template contract

A template turns a site's content into HTML. It is **data, not code**: a package
of markup, a manifest, and a stylesheet. Nothing in it executes.

That is the load-bearing rule. Quickieweb renders templates from a shared
library, in one process, for many sites at once. A template that could run
JavaScript in the renderer would be remote code execution against every tenant
simultaneously. So the engine has no `eval`, no function calls, no expressions —
just an AST walked against a fixed data model.

Everything else in this document follows from that, or from a second rule:
**reading a page must not require JavaScript.** A template produces real HTML.

Check your work with:

```bash
node cli/validate-template.mjs path/to/template
```

Exit code 0 means it is publishable. The validator resolves every `{{path}}` in
every layout against the data model below, so a misspelled field is an error
with a line number rather than a blank space on a published page.

---

## The package

```
template.json          the manifest -- the only file with a fixed name
layouts/index.html     the front page
layouts/article.html   one post
layouts/page.html      one static page
layouts/404.html       not found
partials/*.html        reusable fragments
assets/style.css       the stylesheet
assets/*               fonts and images, if any
```

Layout and partial filenames are yours; the manifest maps names to paths.

### `template.json`

```json
{
  "id": "journal",
  "name": "Journal",
  "version": "1.0.0",
  "engine": "quickieweb-template@1",
  "description": "One line for the library listing.",
  "author": "You",
  "license": "MIT",
  "supports": ["article", "podcast", "gallery", "page"],

  "layouts": {
    "index": "layouts/index.html",
    "article": "layouts/article.html",
    "page": "layouts/page.html",
    "404": "layouts/404.html"
  },
  "partials": {
    "head": "partials/head.html",
    "card": { "path": "partials/card.html", "context": "post" }
  },
  "styles": ["assets/style.css"],

  "tokens": {
    "color.ink": { "type": "color", "default": "#14161a", "label": "Body text", "group": "Color" }
  }
}
```

- **`id`** lowercase letters, digits and hyphens. It is the library key.
- **`version`** semver, and **immutable once published**. Sites pin versions;
  republishing over one would silently change every site that pinned it. Bump it.
- **`supports`** must include `page`. Static pages are a platform feature, not a
  template's choice: a site that switches templates must not lose its About page.
- **`partials`** may be a bare path, or `{ path, context }`. Declare a context
  when the partial is rendered inside `{{#each posts}}` and reads bare fields —
  without it the validator has no way to know what `{{title}}` means and cannot
  check it.

## The language

A Handlebars subset. If you know Handlebars you already know it; the difference
is what is *missing*.

```handlebars
{{ path }}                         escaped interpolation
{{{ path }}}                       raw -- only for fields documented as HTML
{{#if path}} … {{else}} … {{/if}}
{{#unless path}} … {{/unless}}
{{#each path}} … {{else}} … {{/each}}
{{> partial}}
{{! a comment }}
```

Inside `{{#each}}`: `{{.}}` is the current item, and `{{@index}}` (0-based),
`{{@number}}` (1-based), `{{@first}}`, `{{@last}}` are the loop metadata.

Paths are dotted and resolve innermost-first, so `{{site.name}}` works inside a
loop over posts.

**Not supported, deliberately:** expressions, helpers with arguments,
subexpressions, filters, partial parameters, `{{^…}}`. Each one is a step toward
a language, and a language in a template is an execution surface. Use `{{#unless}}`
where you would reach for `{{^}}`.

### Falsiness

`{{#if}}` treats `undefined`, `null`, `false`, `""`, `0` and `[]` as false. So
`{{#if post.tags}}` is the right way to ask whether there are any tags, and
`{{#if post.source}}` the right way to ask whether a post has a source.

## Design tokens

Tokens are the customization contract. Whatever you declare becomes a form field
in the admin — a colour picker, a font selector, an image upload — and a CSS
custom property in the generated `/assets/theme.css`.

```json
"tokens": {
  "color.ink":   { "type": "color",  "default": "#14161a", "label": "Body text", "group": "Color" },
  "font.body":   { "type": "font",   "default": "system-ui, sans-serif", "label": "Body font" },
  "logo":        { "type": "image",  "optional": true, "label": "Masthead logo" },
  "measure":     { "type": "select", "default": "34rem", "options": [
                     { "value": "30rem", "label": "Narrow" },
                     { "value": "34rem", "label": "Standard" }] }
}
```

A token key becomes:

| | |
|---|---|
| `color.ink` in the manifest | what you declare |
| `{{theme.color.ink}}` | how a layout reads it |
| `var(--color-ink)` | how the stylesheet reads it |

Every non-optional token needs a `default`. A key that is a prefix of another
(`color` alongside `color.ink`) is rejected, because tokens nest.

**Put every colour, font and measure in a token.** A value hardcoded in your CSS
is a value the customer cannot change, and "add a colour picker" then means
forking the template.

### Dark mode

Declare a parallel `dark.*` set and remap in your own stylesheet:

```css
@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) {
    --color-ink:   var(--dark-color-ink);
    --color-paper: var(--dark-color-paper);
  }
}
:root[data-theme="dark"] { /* the same remapping, so an explicit choice wins */ }
```

That way a customer who picks a brand accent picks its dark counterpart too,
rather than inheriting whatever you chose.

### Webfonts are self-hosted

```json
"webfonts": [{ "family": "Inter", "src": "assets/inter.woff2", "format": "woff2" }]
```

The file ships inside the package. Linking Google Fonts is rejected by the
validator: it is a third-party request on every page load of every site using
your template, and a dependency that can break a customer's site without anyone
touching it.

## Search

Search is platform behaviour, not template code. `renderSite` emits
`search-index.json` and `assets/search.js` for every site; a template supplies
the markup and the styling. Same split as design tokens.

Opt in with three hooks and by rendering `template.scripts`:

```html
<form class="search" data-qw-search hidden role="search">
  <input type="search" data-qw-search-input placeholder="Search" aria-label="Search this site">
  <div class="search-results" data-qw-search-results hidden></div>
</form>

{{#each template.scripts}}<script src="{{.}}" defer></script>{{/each}}
```

`hidden` on the form is load-bearing: the script removes it, so a reader without
JavaScript never sees a control that cannot work. A template that omits the
hooks simply has no search, and the script exits without touching the page.

The index is fetched on the first interaction with the box — never on page load —
so a reader who does not search pays nothing for the feature existing.

Results are rendered into the panel with these classes, which your stylesheet
owns: `.qw-s-hit` (a result, `.is-active` when keyboard-selected), `.qw-s-title`,
`.qw-s-meta`, `.qw-s-dek`, `.qw-s-msg` (empty and error states), and `<mark>`
around matched words.

Behaviour you get for free: type to search, `/` to focus from anywhere, ↑↓ to
move, Enter to follow, Escape and click-outside to close, an empty query that
lists everything, and `?q=` in the URL so a search is shareable.

## Rules the validator enforces

| Rule | Why |
|---|---|
| `<script>` only as `<script src="{{…}}">` with no body | Reading a page must not need JavaScript. The one permitted form takes its URL from the view model — `{{#each template.scripts}}` — so a template ships no JavaScript of its own. Structured data is `{{{seo.jsonLd}}}`, already wrapped. |
| No external `href`/`src` (`https://…`) on assets | Templates are self-contained. A third-party request is a dependency and a tracking vector nobody chose. |
| No `@import` of a remote stylesheet | Same. |
| Every `{{> name}}` is declared in `partials` | A missing partial is a render-time 500 across the whole site. |
| Every `{{path}}` resolves against the data model | Otherwise a typo publishes as a blank space. |
| Every manifest-named file exists | |
| All four required layouts present and compiling | |
| The whole package renders a fixture | Catches what static checks miss: self-including partials, a layout that never opens `<html>`. |

The fixture is deliberately awkward — a post with every field, a post with
nothing optional, a podcast episode, a gallery, and a page. If your template
renders all five, it renders any real site.

## Galleries

A `gallery` is a dated post that carries an image set: the same shape a
`podcast` has, with pictures instead of an audio file. Images are authored
inline in the body and split out into `post.images` when the record is saved, so
`post.bodyHtml` is the prose that was around them.

Render the grid yourself and let the platform handle the viewer:

```html
{{#if post.images}}  <div class="gallery" data-qw-gallery>
{{#each post.images}}    <figure class="gallery-item" data-qw-gallery-item>
      <img src="{{url}}" alt="{{alt}}" loading="lazy"{{#if width}} width="{{width}}"{{/if}}{{#if height}} height="{{height}}"{{/if}}>
{{#if caption}}      <figcaption>{{caption}}</figcaption>
{{/if}}    </figure>
{{/each}}  </div>
{{/if}}
```

`assets/gallery.js` is emitted for every site and linked through
`{{#each template.scripts}}`, exactly like search. It finds those two
attributes, reads the `src`, `alt` and `<figcaption>` back out of your markup,
and opens a lightbox on click with keyboard, swipe and wrap-around paging. There
is no manifest to fetch and nothing to keep in sync; with JavaScript off, the
grid is still a grid of real images.

You style the grid. The overlay ships its own CSS, because a modal image viewer
is not a thing each template should have to reimplement, and you can retune it
through `--qw-lb-backdrop` and `--qw-lb-ink`.

Two more fields are yours if you want them: `post.isGallery` for a chip beside
the date, and `post.cover` (the first image, or `null`) for a thumbnail on an
index card.

A gallery renders through your `article` layout. Declare an optional `gallery`
layout only if you want it to look different — there is no obligation, and
`supports` is what says you handle the type at all.

## Writing one

1. Copy `templates/plain` — it is the smaller of the two.
2. Change `id`, `name`, `version`, `description` in `template.json`.
3. Edit the layouts. Read the generated table above for what is in scope where.
4. `node cli/validate-template.mjs templates/yours`
5. `node cli/build.mjs --template yours` and open `site/index.html`.
6. `node cli/templates.mjs publish templates/yours`

### If you are an LLM

Read this document and then run the validator. Do not guess at field names —
`post.headline` does not exist, it is `post.title` — and do not skip step 4,
because a template that renders nothing renders it silently. The validator's
error messages list what *is* available at the point where you went wrong.
